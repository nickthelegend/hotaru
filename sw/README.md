# HOTARU 3 — built in SolidWorks

HOTARU 3 is the v2 lamp rebuilt as native SolidWorks parts, because v2's arm
was not stiff enough and its shoulder servo was working too hard. Every part
is a real SolidWorks part with a named feature tree (sketches, extrudes,
cuts, revolves), generated by the Python in this folder through the
SolidWorks API. Open any `.SLDPRT` in `solidworks/parts/` and edit it by hand
like any other part.

| | |
|---|---|
| parts + assembly | `solidworks/parts/*.SLDPRT`, `solidworks/HOTARU3.SLDASM` |
| **print plates (P1S)** | [`exports/v3/plates/`](../exports/v3/plates/): 5 plates as 3MF + STL, settings inside |
| single parts | `exports/v3/print/*.stl`, already in print orientation, Z up |
| firmware | `firmware/hotaru_motion/hotaru_motion.ino` (PCA9685) |

## What changed from v2, and why

| | v2 | HOTARU 3 |
|---|---|---|
| shoulder | servo spline carries the whole arm, direct drive | **1.8 : 1 printed gear** (30T pinion → 54T gear cut into link1's plate). link1 pivots on two O14 journal pins in the tower, so the servo spline carries torque only |
| links | two flat 4 mm plates, printed standoffs, truss cutouts | **box sections**: a plate with two full-length walls, closed by a second plate bolted on with M3 |
| joint pins | printed threaded stubs | printed O14 journal pins, one M3 each to stop them sliding out |
| fasteners | printed P6 thumb-bolts | **M3 socket-head bolts and M3 hex nuts everywhere**, nuts in printed pockets and slide-in slots |
| pan | disc rides the tub rim, loose | disc rides a 10 mm slew ring, **trapped by a bolted lip ring** with a 45° lip. The pan horn sits in a pocket with float both ways, so the pan servo carries torque only |
| servo driver | servos on ESP32 GPIO | **PCA9685** in the base, pulses staggered across the frame |
| motion | constant-speed steps | synchronised trapezoid profile + a pose guard (torque and self-collision) |

Nothing is bought beyond the four MG996Rs, M3 bolts/nuts, the PCA9685 and
the electronics v2 already used. No bearings, springs or metal horns.

## Proof that it works (checked in SolidWorks, not by eye)

Run `python sw/h3_all.py` to repeat all of it.

* **Interference**: the assembly is driven to 12 named poses covering every
  joint's range (pan ±90°, shoulder −30…+70°, elbow ±120°, head ±75°), and
  SolidWorks' own Interference Detection runs at each one. **All 12 are clear.**
  `solidworks/pose_report.json`, screenshots in `solidworks/shots/pose-*.png`.
* **Servo load**: SolidWorks mass properties of every real part, posed over a
  grid covering the full range. Worst case per servo, against MG996R stall
  (0.92 N·m at 4.8 V):

  | servo | worst case | of stall |
  |---|---|---|
  | shoulder (after the 1.8 : 1 gear) | 0.283 N·m | **30.7 %** |
  | elbow | 0.207 N·m | 22.5 % |
  | head | 0.020 N·m | 2.2 % |

  All under one third of stall, the level a hobby servo can hold all day.
  Direct-drive, the shoulder would sit at 55 % in the same pose.
  Estimated using PLA at 75 % print fill, which is conservative.
* **Pose guard vs SolidWorks**: 40 random poses. The guard allowed 38, and
  SolidWorks found all 38 collision-free. It refused 2: one really collides,
  the other is clear (the guard errs on the safe side). **0 misses.**
  `solidworks/guard_report.json`.
* **The base turning, whole range** (`python sw/h3_pan_sweep.py`,
  `solidworks/pan_report.json`, 1350 poses in SolidWorks). The MX pod is the
  one fixed part above the turntable, so it is what a panning arm can hit.
  * 23 arm configurations × pan −90…+90° in 5° steps (851 poses). The guard
    allowed 785 of them; **SolidWorks found 0 of those interfering**. Every
    preset pose is clear at every pan angle.
  * The old firmware guarded only a move's END pose. Panning from −60° to
    +60° with the arm folded back low was allowed, and SolidWorks shows the
    shade going through the keycap and switch on the way (7 of the sampled
    poses). The firmware now checks the whole path and goes round:
    arm up, pan, arm down. **Every planned route and every button/demo move:
    0 interferences.**
  * `node firmware/sim/sim.mjs` runs the firmware's own motion code off the
    board (LLVM clang → WebAssembly): the pod routes, the button cycle, a
    new command mid-pan, and 5000 random targets. No frame enters a
    keep-out.
  * The pan servo now engages last at power-up, after the arm is back at
    rest, so a drooped arm is never swung across the pod.
* **Firmware**: clang syntax/type check with `-Wall -Wextra`, clean. The
  motion planner was simulated: joints arrive together, 0° overshoot, peak
  speed exactly at the 90°/s limit. It has **not** been flashed to a board
  here.

## Bill of materials

**Printed** (`exports/v3/print/`, P1S bed, no supports):
tub, lipring, disc, tower, pinion, link1, link1-cover, link2, link2-cover,
head, head-cover, shade, ledclamp, keycap, pin-shoulder ×2, pin-elbow,
pin-head.

**M3 hardware**, all ISO 4762 socket head + ISO 4032 hex nut:

| bolt | qty | where |
|---|---|---|
| M3×8 | 1 | shade hub → head servo shaft |
| M3×10 | 29 | servo tabs ×16 (4 servos), link1 cover ×6, link2 cover ×4, link2 hub → elbow shaft, pinion → shoulder shaft, head cover top |
| M3×12 | 12 | lip ring ×6, tower → disc ×4, elbow pin, head pin |
| M3×16 | 6 | shoulder pins ×2, head block ↔ link2 ×4 |
| **M3 nut** | **45** | |

The elbow-pin and head-pin bolts reach about 1.4 mm into their nut. They
only stop the pin sliding out and carry no load.

**Bought, unchanged from v2**: 4× MG996R (the stock horns: two used whole,
two **trimmed to 30 mm tip-to-tip** with side cutters, for the pinion and the
shade), ESP32-S3 dev board, PCA9685 16-ch board, MAX98357A, INMP441,
2040 speaker, WS2812 12-LED ring, Cherry MX switch, 2200 µF capacitor.

## Measure this before you print

`HORN_TOP` in `sw/h3.py` is **9.0 mm**: from the servo case top to the outer
face of a horn pressed onto the spline. It is not measured. Every joint
stack is built around it with 1 mm of axial float, so ±1 mm is absorbed.
Measure one of your servos, and if it's more than a millimetre off, change
the number and re-run `python sw/h3_all.py`.

## Wiring

PCA9685 VCC→3V3, GND→GND, SDA→GPIO8, SCL→GPIO9. Servos on channels
0 pan, 1 shoulder, 2 elbow, 3 head. V+ from the 5 V rail, split at the USB-C
input, with the 2200 µF across the V+ terminal. MX key GPIO4 → GND.
USB-C 5 V is the limit here: four MG996Rs moving together can pull more than
a 3 A supply. The firmware spreads that out (staggered pulses, engaging one
servo at a time, acceleration-limited moves), but a weak USB supply will
still brown out.

## The scripts

| file | does |
|---|---|
| `swlib.py` | the SolidWorks API layer: sketches, extrude/cut/revolve, save, STL. Runs its **own** SolidWorks process (see below) |
| `h3.py` | every number |
| `hotaru3.py` | one builder function per part |
| `h3_build.py` | build parts → `.SLDPRT` + STL |
| `h3_assembly.py` | the assembly, the poses, SolidWorks interference at each |
| `h3_torque.py` | worst-case servo torque from SolidWorks mass properties |
| `h3_guard.py` | the firmware's pose guard in Python, validated against SolidWorks |
| `h3_stl.py` | STLs into print orientation |
| `h3_plates.py` | lays the parts out on five P1S plates → 3MF / STL / SVG |
| `h3_film.py` / `h3_replay.py` | the SolidWorks timelapse |
| `h3_all.py` | everything, in order |

**One SolidWorks per automation.** `Dispatch("SldWorks.Application")`
attaches to whichever SolidWorks is already running. During this build,
another automation session was driving that same SolidWorks, and each side
kept closing the other's documents. Every "object has disconnected" failure
came from that. `swlib.dedicated_session()` starts this project's own
SLDWORKS.exe and always reattaches to it by process id through the Running
Object Table.
